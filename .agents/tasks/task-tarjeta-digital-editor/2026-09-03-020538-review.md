# Editor de tarjeta digital con dos plantillas, flip 3D y modelo de datos ampliado (v1)

La tarjeta del cliente pasa de un visor de una sola cara a una tarjeta con giro 3D, dos plantillas de anverso (Editorial y Ejecutiva) que comparten reverso interactivo, y un editor renovado con selector de plantilla, gestor de píldoras, switches de contacto y vista previa girable en vivo. El modelo de datos crece con `template`, `estadoPill`, `pildoras[]`, `contactos{}` y `reverso{}` sobre una migración SQL aditiva e idempotente que no toca columnas existentes, para no romper las tarjetas ya activas. El aislamiento del mundo tarjeta (`getGiftCardSupabase`, RPC vía `callClientRpc`) y las firmas de los tres RPC se conservan intactos.

**Watch for:** el botón "Guardar Contacto" nunca incluye el correo y no se habilita cuando el correo es el único dato de contacto, porque `buildVCard`/`canBuildVCard` leen `card.email` (nivel superior) mientras el modelo normalizado guarda el correo en `card.contactos.email` (**confirmed**). El resto es sólido: el patrón de flip Safari-safe está bien replicado, la restricción de hosts de vídeo está bien cerrada, y lint/build siguen en verde (12 warnings, 0 errores).

**Verdict**: NEEDS_CHANGES

## High-level view

El modelo de datos se unifica en `cardData.js` como helper puro: normaliza la respuesta del RPC hacia el front (`normalizeCardData`) y construye el patch de guardado (`toSavePatch`), con el mapeo `pildoras ↔ specialties` y `contactos`/`reverso` empaquetados en la columna jsonb `card_extra`. `phone` y `whatsapp` se quedan como columnas propias. La migración es aditiva (`add column if not exists`) y recrea las tres funciones con las mismas firmas, con `template` default `'editorial'` para que ninguna tarjeta vieja quede sin plantilla válida.

El giro 3D de `DigitalCard.jsx` replica el patrón Safari-safe de producción con las propiedades prefijadas en estilos en línea, y `resolveVideo` cierra la lista de hosts del reverso a YouTube/Loom/Vimeo más archivos conocidos — decisión correcta para una página pública sin sesión. El botón de reserva se degrada a WhatsApp cuando falta la agenda.

El punto que bloquea es el puente entre el modelo normalizado y el generador de vCard: el editor guarda el correo bajo `contactos.email`, pero el `.vcf` se construye leyendo un `email` de nivel superior que nunca existe, así que el correo no llega al contacto y no cuenta para habilitar el botón.

### El correo se pierde entre `contactos.email` y la vCard

`normalizeCardData` coloca el correo en `contactos.email` y el editor lo guarda ahí (`buildCardData` arma `contactos: { …, email }`). Pero `SaveContactButton` invoca `buildVCard(card)` y `canBuildVCard(card)`, y ambos helpers leen `card.email` a nivel superior:

```js
// vcard.js
export function canBuildVCard(card) {
  return Boolean(
    String(card.fullName ?? '').trim()
    && (phoneValue(card.phone) || phoneValue(card.whatsapp) || String(card.email ?? '').trim()),
  );
}
// buildVCard: const { fullName, title, company, phone, whatsapp, email } = card;
```

Como el modelo normalizado nunca pone `email` en el nivel superior, dos cosas fallan (**confirmed**): la línea `EMAIL` no se emite aunque el dueño haya llenado el correo, y una tarjeta cuyo único contacto sea el correo (sin teléfono ni whatsapp) muestra el botón "Guardar Contacto" apagado. El arreglo mínimo es pasar el correo al llamar los helpers desde `SaveContactButton` (`buildVCard({ ...card, email: card.contactos?.email })`) o, mejor, que `buildVCard`/`canBuildVCard` lean `contactos.email` con respaldo al nivel superior para no romper otros llamadores.

### Guardado autoritativo de píldoras vacías

`toSavePatch` siempre emite `pildoras` como array (nunca ausente), así que `save_gift_card` ejecuta `specialties = coalesce(p_patch->'pildoras', …, specialties)` con un `[]` real cuando el dueño no tiene etiquetas. `[]` no es NULL, de modo que un guardado con cero píldoras sobrescribe `specialties` con vacío (**confirmed**). Es el resultado deseado —el editor siembra las píldoras desde `specialties`, así que un guardado normal las preserva— pero cualquier guardado es autoritativo sobre las etiquetas; no hay merge parcial de píldoras como sí lo hay para `card_extra`. Fuera de esto la migración sólo añade columnas y recrea las tres funciones con firma idéntica: `my_gift_card` conserva todos los campos base y suma `template`/`estadoPill`/`cardExtra`, y `public_gift_card` mantiene `canPropagate`.

### Flip 3D Safari-safe: el detalle del pointer-events

La cara oculta añade `pointer-events-none` además de `backface-visibility: hidden`, cubriendo el hueco de que `backface-visibility` esconde la cara de espaldas a la vista pero no al toque —sin eso, los enlaces del anverso seguirían siendo pulsables a través del reverso—. El `overflow-hidden` se deja en cada cara y no en el elemento que gira, para no aplanar la escena 3D.

### Restricción de hosts de vídeo y control de audio

`resolveVideo` sólo devuelve algo reproducible para YouTube, Loom, Vimeo y archivos de vídeo conocidos (incluido Cloudinary), y cae a vacío para cualquier otro host; como la tarjeta se abre desde un enlace público sin sesión, esto evita que el campo de vídeo se convierta en un `iframe` hacia contenido arbitrario. El control de silenciar/activar audio se ofrece sólo para `<video>` de archivo, no para los `iframe` de terceros donde no se puede gobernar desde fuera.

### Degradado del botón de reserva a WhatsApp

Cuando el reverso no trae `bookingUrl`, `CardBack` cae a `whatsAppLink(card.whatsapp || card.phone, …)`. Si tampoco hay número, `whatsAppLink` devuelve `https://wa.me/?text=…` sin destinatario (comportamiento documentado en `advisorPhone.js`): abre WhatsApp con el texto puesto y deja elegir contacto. Es un fallo abierto deliberado, pero en el reverso el botón se anuncia como "Agendar" y no llevar a nadie puede confundir. Vale la pena ocultarlo cuando no hay ni agenda ni número.

### Extracción del editor y wrapper de compatibilidad

`CardEditor` sale de `GiftCardPage.jsx` a su propio archivo conservando firma (`cardId`, `initial`, `deviceSecret`) y lógica de guardado, subida de foto y compartir; `GiftCardVisual` queda como wrapper delgado sobre `DigitalCard` para no tocar los imports existentes. El editor arranca los switches de contacto encendidos sólo para los canales que ya traían dato, de modo que una tarjeta vieja no esconde de golpe lo que mostraba. Los inputs del editor usan `text-[16px]` y el `INPUT` de las pantallas de acceso en `GiftCardPage` también se subió a `text-[16px]`, cerrando el zoom de Safari iOS.

Sobre Instagram: el editor usa `IdCard` como marcador del switch y `DigitalCard` dibuja un `InstagramMark` SVG en línea porque esta versión de `lucide-react` no exporta `Instagram` (rompería el build con MISSING_EXPORT). Es una limitación real de la librería, la misma salida que ya se hace con WhatsApp.

### Sin pruebas automáticas

No hay tests unitarios en el repo y esta tarea no añade ninguno. **No probado:** el guardado extremo-a-extremo contra el RPC (no hay BD local en este entorno), el merge superficial de `card_extra` al guardar sólo `contactos` o sólo `reverso`, y el render de la vCard con correo tras corregir el mapeo. Los helpers puros (`cardData.js`, `videoEmbed.js`, `vcard.js`) son candidatos naturales a pruebas de unidad.
